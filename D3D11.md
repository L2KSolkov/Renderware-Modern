# RenderWare — Direct3D 11 render target (D3D9 retained)

## Context

`RWSDK/` now builds through CMake with `RW_TARGET` selecting the render target: `d3d9` (default), `d3d8`, `opengl` and `null` are implemented, the console targets are stubs. This adds a fifth implemented target, **`d3d11`**, sitting alongside D3D9 as a peer. **No D3D9 file is modified** — the only shared files touched are the target registries that must learn the new name.

The D3D9-specific code is ~76k LOC: `driver/d3d9` 26k, `world/pipe/p2/d3d9` 16k, `src/pipe/p2/d3d9` 1.5k, and 33k across 11 plugins. It is overwhelmingly fixed-function — 791 `RwD3D9SetTextureStageState` and 345 `RwD3D9SetRenderState` calls — and D3D11 has no fixed-function pipeline, no texture stage states, no `D3DX`, and immutable state objects instead of per-state setters. The `.vsh`/`.psh` shaders that do exist are `vs.1.1` assembly, which SM5.0 cannot consume.

**The seam that makes this tractable** is RenderWare's own render-state abstraction. Core and plugin code above the driver calls `RwRenderStateSet`, which the device dispatches to `_rwD3D9RWSetRenderState` / `_rwD3D9RWGetRenderState` (`driver/d3d9/d3d9rendst.c`, wired at `driver/d3d9/d3d9device.c:4524`). Porting means implementing that same bounded contract against D3D11 state objects and explicit shaders — not translating 791 raw texture-stage calls.

### Decisions taken

| Decision | Choice |
|---|---|
| Architecture | **Shader-first rewrite** — no fixed-function emulation; explicit HLSL and D3D11 state objects throughout |
| Phasing | Core first (`rwcore` + `rpworld`), plugins after in dependency order |
| Minimum | Feature level **11_0**, shader model **5.0** |
| Shaders | HLSL sources compiled by `fxc` at build time into byte-array headers |
| Examples | **Phase 7, deferred — not to be started until explicitly requested** |

A note on the shader-first choice: it means the ~49k LOC of pipeline and plugin D3D9 code is *rewritten* against explicit shaders rather than ported call-for-call. That is the larger amount of work, and it is what was chosen. The conventions below keep the result recognisably RenderWare despite the rewrite.

## Conventions (binding on every file this project adds)

Derived from `driver/d3d9/`, `world/pipe/p2/d3d9/` and `src/pipe/p2/d3d9/`. Deviations are defects.

**Directories** — mirror the D3D9 layout exactly: `driver/d3d11/`, `src/pipe/p2/d3d11/`, `world/pipe/p2/d3d11/`, `plugin/<name>/d3d11/`.

**File names** — mechanical `<target><module>.c` substitution of the D3D9 names, including the awkward ones: `d3d9device.c` → `d3d11device.c`, `d3d92drend.c` → `d3d112drend.c`, `d3d9convrt.c` → `d3d11convrt.c`, `d3d9raster.c` → `d3d11raster.c`, `d3d9rendst.c` → `d3d11rendst.c`, `d3d9texdic.c` → `d3d11texdic.c`, `d3d9dxttex.c` → `d3d11dxttex.c`, `d3d9vertexbuffer.c` → `d3d11vertexbuffer.c`, `d3d9metric.c` → `d3d11metric.c`. `dds.h`, `drvfns.h`, `drvmodel.h`, `drvequat.c` keep their names.

**Capitalisation is inconsistent in the original and must be reproduced**: `world/pipe/p2/d3d9/` holds `D3D9lights.c` and `D3D9pipe.c` (capital) beside `d3d9usage.c`, `d3d9vertexshader.c`, `d3d9vertexshaderutils.c` (lower). So: `D3D11lights.c`, `D3D11pipe.c`, `d3d11usage.c`, `d3d11vertexshader.c`. Pipeline nodes keep the `nodeD3D11AtomicAllInOne.c`, `nodeD3D11WorldSectorAllInOne.c`, `nodeD3D11SubmitNoLight.c` form. `d3d9vertexdeclaration.c` becomes **`d3d11inputlayout.c`** — RW names these files after the API concept, and D3D11's concept is the input layout.

**Symbols** — `RwD3D11*` public, `RpD3D11*` plugin-facing, `_rwD3D11*` internal functions, `_RwD3D11*` internal globals, `RxD3D11*` pipeline types. Macro forms of hot entry points follow `drvfns.h`: `_rwD3D11SetVertexShaderMacro` with a `#define RwD3D11SetVertexShader _rwD3D11SetVertexShaderMacro` / non-macro pair switched on `RWDEBUG`.

**Source form** — the file banner block (`Module :` / `Purpose :`); `/* RWPUBLIC */` … `/* RWPUBLICEND */` around anything `incgen` must lift into `rwcore.h`; include guards `D3D11DEVICE_H`, `D3D11_DRVMODEL_H`; `RWFUNCTION(RWSTRING("..."))` in internals and `RWAPIFUNCTION(RWSTRING("..."))` in public entry points, paired with `RWRETURN` / `RWRETURNVOID`; `RWASSERT` for preconditions; `RWERROR` for failures; `MACRO_START` / `MACRO_STOP` around multi-statement macros; `DXCHECK(fn)` around every D3D call, defined to `_rwD3D11CheckError` under `RWDEBUG` and to `(fn)` otherwise; Doxygen `\ingroup rwcoredriverd3d11` on public types.

## Phase 1 — Target registration

The smallest change set that makes `RW_TARGET=d3d11` a real, selectable target that configures and links an empty driver.

- `src/plcore/badevice.h:134–147` — add `#define rwDEVICE_D3D11 (9)`, honouring the file's own instruction to append to the end of the list.
- `cmake/RWOptions.cmake:102–105` — add `d3d11` to `RW_TARGET`'s docstring and `STRINGS` property.
- `cmake/targets/d3d11.cmake` — new, modelled on `cmake/targets/d3d9.cmake` but **without** `find_legacy_dxsdk()` or the compat-header staging: `d3d11.h`, `dxgi.h` and `d3dcompiler.h` all ship in the modern Windows SDK. Links `d3d11.lib`, `dxgi.lib`, `dxguid.lib`. No `d3dx` equivalent exists, so the `RW_WORLD_LIBS` d3dx9 entry has no counterpart — the utilities it provided are replaced in Phase 5.
- `cmake/pipes-p2.cmake` — add the `d3d11` branch listing `RW_PIPE_PS_CSRC` and `RW_WORLD_PIPE_PS_CSRC`.
- `driver/d3d11/drvmodel.h` — the `RwIm2DVertex` contract. `RwD3D11Vertex` keeps D3D9's field layout (`x y z rhw emissiveColor u v`) so the `RwIm2DVertexSet*` macro family ports unchanged; `rhw` becomes a shader-consumed field rather than an FF one. `RxVertexIndex` stays `RwUInt16`. `RwD3D11Metrics` mirrors `RwD3D9Metrics` with the counters that survive (`numVBSwitches`) plus D3D11-shaped ones (`numStateObjectChanges`, `numShaderChanges`, `numConstantBufferUpdates`).
- `driver/d3d11/drvfns.h`, `d3d11device.h`, `drvequat.c` — skeletons.
- `CMakePresets.json` (root and `RWSDK/`) — `win32-d3d11-debug`, `win32-d3d11-release`.

Checkpoint: `cmake --preset win32-d3d11-release` configures, `rwcore` links, `rwcore.h` generates with the D3D11 driver model in it.

## Phase 2 — Device, presentation and the standards contract

`driver/d3d11/d3d11device.c` is the largest single file (D3D9's is 213 KB). It owns:

- **Device creation** — `D3D11CreateDeviceAndSwapChain` at FL 11_0, `DXGI_SWAP_CHAIN_DESC` from the RW video-mode selection. Globals `_RwD3D11Device`, `_RwD3D11DeviceContext`, `_RwD3D11SwapChain`, `_RwD3D11RenderTargetView`, `_RwD3D11DepthStencilView`, `_RwD3D11DeviceCaps`, mirroring the `_RwD3DDevice` / `_RwD3D9RenderSurface` set in `d3d9device.h:45–61`. The D3D9 device is one object; D3D11 splits device and immediate context, and both are exposed (`RwD3D11GetCurrentD3D11Device`, `RwD3D11GetCurrentD3D11DeviceContext`).
- **The `rwDEVICESYSTEM*` switch** — all 22 cases D3D9 handles (`d3d9device.c:2302–2546`), with `rwDEVICESYSTEMGETID` returning `rwDEVICE_D3D11`. Adapter and mode enumeration moves from `IDirect3D9::EnumAdapterModes` to `IDXGIFactory` / `IDXGIAdapter` / `IDXGIOutput`.
- **The 25 standards** (`rwD3D11Standards[]`, mirroring `d3d9device.c:2076–2130`): camera begin/end/clear, `rwSTANDARDRASTERSHOWRASTER`, RGB↔pixel, raster set/get image, raster create/destroy, `rwSTANDARDIMAGEFINDRASTERFORMAT`, texture set raster, raster lock/unlock and palette lock/unlock, raster clear and clear-rect, the three raster render entries, set raster context, sub-raster, the three native-texture serialisation entries, and get-mip-levels. Phase 2 lands camera and show-raster; the raster group is Phase 3.

Checkpoint: an app opens a window, `RwCameraClear` fills it, `RwCameraShowRaster` presents.

## Phase 3 — Rasters and textures

`d3d11raster.c`, `d3d11convrt.c`, `d3d11texdic.c`, `d3d11dxttex.c`, `dds.h` complete the standards table.

The substantive differences from D3D9: no `D3DPOOL_MANAGED`, so lock/unlock becomes staging-resource `Map`/`Unmap` with an explicit upload path; `D3DFMT_*` becomes `DXGI_FORMAT_*` in `d3d11convrt.c`; palettised formats have no D3D11 equivalent and must be expanded on upload (`driver/common/palquant.c` already does the quantisation side); BC1–BC3 replace DXT1–DXT5 by name only, so the DDS reader ports directly. Native texture serialisation must keep reading D3D9-written streams — the on-disk format is content, not API state.

## Phase 4 — Shader system and immediate mode 2D

`driver/d3d11/d3d11shader.c/.h` is the piece with no D3D9 counterpart: the shader library and permutation cache that replaces the fixed-function pipeline. It keys on the state the RW layer actually sets — texture present, alpha test, fog, vertex colour, lighting — and hands back a compiled `ID3D11VertexShader` / `ID3D11PixelShader` pair plus its input layout.

`d3d11rendst.c` implements the seam: `_rwD3D11RWSetRenderState` / `_rwD3D11RWGetRenderState`, wired into the `RwDevice` vtable where `d3d9device.c:4524` wires the D3D9 pair. Each `RwRenderState` maps to a cached `ID3D11BlendState`, `ID3D11DepthStencilState`, `ID3D11RasterizerState` or `ID3D11SamplerState`, plus a permutation key bit where the state changes shading rather than pipeline state. State objects are hashed and reused; this file also owns the constant buffers holding the transform, material and light data D3D9 passed through `SetTransform` / `SetMaterial` / `SetLight`.

`cmake/RWCodegen.cmake` gains `rw_compile_hlsl()`, mirroring the existing `rw_generate_rpe()` / `rw_generate_public_header()` helpers: `fxc /T vs_5_0|ps_5_0 /Fh <out>.h /Vn dw<Name>`, so the emitted symbol keeps the `dw<Name>` spelling the D3D9 headers use (`dwToonVertexShader` in `plugin/toon/d3d9/toonvertexshader.h`) and call sites read the same. HLSL lives beside the D3D9 assembly it replaces: `plugin/toon/d3d11/toonvertexshader.hlsl`.

`d3d112drend.c` and `src/pipe/p2/d3d11/{im3dpipe.c,nodeD3D11SubmitNoLight.c}` then render immediate-mode 2D and 3D through that system.

Checkpoint: textured, alpha-blended, fogged 2D and im3D geometry on screen.

## Phase 5 — World and atomic pipelines

`world/pipe/p2/d3d11/`: `D3D11pipe.c`, `D3D11lights.c`, `d3d11usage.c`, `d3d11inputlayout.c`, `d3d11vertexshader.c`, `d3d11vertexshaderutils.c`, `d3d11vertexshaderdefs.h`, `nodeD3D11AtomicAllInOne.c`, `nodeD3D11WorldSectorAllInOne.c`, `wrldpipe.c`, `native.c` — plus the `RpD3D11GeometryGetUsageFlags` / `RpD3D11WorldSectorSetUsageFlags` API family that `d3d9usage.c` exposes.

Two things get harder and one gets easier. Input layouts require shader bytecode at creation time, so `d3d11inputlayout.c` must pair each vertex format with a signature shader rather than standing alone as `d3d9vertexdeclaration.c` does. The `d3dx9` helpers that `RW_WORLD_LIBS` supplies for D3D9 have no D3D11 equivalent and their uses must be replaced with `DirectXMath` or hand-rolled code. Against that, the vertex shader utilities get simpler: SM5.0 has none of the SM1.1 instruction-count and register limits the current shaders are contorted around.

Checkpoint: `rpworld` renders a lit, textured clump and a world sector.

## Phase 6 — Plugins

Each gets a `plugin/<name>/d3d11/` directory and a `d3d11=` entry in its `TARGET_SOURCES` list, following the pattern in `plugin/skin2/CMakeLists.txt:6–25`. Until a plugin is ported, its CMakeLists omits the `d3d11` entry and `rw_add_plugin` reports it unavailable under `RW_TARGET=d3d11` — the build stays green throughout.

Order follows dependency and risk: **skin2** (largest, and every combination variant depends on it) → **matfx** → **toon** → **team** → **normmap** (these four carry the SM1.x assembly that becomes HLSL) → **patch** → **ptank** → **prtstd**, **prtadv**, **crowd**, **ltmap**.

Note the variant plugins — `rpskinmatfx`, `rpskintoon`, `rpskinmatfxtoon`, `rppatchskinmatfx` and the rest — are built from shared sources with different combinations, so a `d3d11/skind3d11matfxshared.c` serves several libraries exactly as its D3D9 counterpart does.

## Phase 7 — Examples (deferred)

The examples still build against D3D9 and are unaffected. Adding a `d3d11` configuration to them is **out of scope until explicitly requested** — do not start this phase.

## Verification

1. **D3D9 is untouched.** `git diff --stat` shows no change under `driver/d3d9/`, `src/pipe/p2/d3d9/`, `world/pipe/p2/d3d9/` or any `plugin/*/d3d9/`. `win32-d3d9-release` builds all 74 libraries byte-comparably to the pre-change build. Run this at every phase boundary, not just at the end.
2. **Other targets unaffected.** `win32-d3d8-release`, `win32-opengl-release` and `win32-null-release` still configure and build; the `badevice.h` and `RWOptions.cmake` edits are additive.
3. **Per-phase checkpoints** as listed above — each phase ends with something on screen, not just something that links.
4. **Shader build.** `fxc` compiles every `.hlsl` at build time; a deliberate syntax error fails the build rather than surfacing at run time. Generated headers land in the build tree, not the source tree.
5. **Side-by-side comparison.** The same scene rendered under `RW_TARGET=d3d9` and `RW_TARGET=d3d11` should match visually. This is the real acceptance test for the shader-first rewrite and the reason to keep D3D9 building: every divergence is a shader or state-object bug with a working reference one preset away.
6. **Metrics parity.** `RW_METRICS=ON` builds under d3d11 and `RwD3D11Metrics` reports sane counters — this exercises `d3d11metric.c` and the state-object cache's hit rate.
7. **DLL build.** `RW_DLL=ON` with `RW_TARGET=d3d11` links `rwgd3d11.dll` and exports only `Rw`/`Rp`/`Rt` symbols, with no D3D11 or DXGI symbols leaking.

## Out of scope

Examples (Phase 7, gated); feature levels below 11_0; D3D12 or Vulkan; removing or refactoring any D3D9 code; the console targets.
